# Проверка замечаний при передаче проекта

## 1. Неиспользуемый код

Проверены ссылки из Python, URL, шаблонов, настроек статики и сборки. Удалены: `users_backup` (26 резервных шаблонов), восемь старых CSS backup-файлов, неиспользуемый прототип интеграции виджета СДЭК, отдельный каталог референсных ресурсов и два разовых корневых скрипта (один содержал синтаксически некорректную старую правку CSS). Они восстанавливаются из Git-истории; рабочие media и данные клиентов не удалялись. Неиспользуемые Poetry-переменные Docker и зависимость CKEditor 5 также убраны.

Активные модели Recipe/RecipeStep, blog/pages/users и CKEditor 4 не удаляются по одному отсутствию прямого Python-импорта: они участвуют в админке, шаблонах, API, сигналах и исторических миграциях. CKEditor 4 остаётся известным отдельным риском; замена требует переноса полей/данных, а не удаления библиотеки из requirements. Проверка четырёх пользовательских CSS-файлов не выявила полностью идентичных повторных правил внутри одинакового CSS-контекста. Рабочие cascade overrides не объявлены мусором и не удалялись без доказательства.

## 2. Миграции

На исходной проверенной версии `b2f6a6581d6e4e4a9f6eff258620a578c37042e9` полный `migrate` в новой SQLite БД прошёл, `makemigrations --check` не выявил расхождений. Указанного удаления Recipe/RecipeStep в этой версии истории нет; переписывать применённые миграции для устранения отсутствующей операции нельзя.

Добавлены тест рендеринга полного исторического состояния и тест обновления с `catalog.0047` на новую `0048` с сохранением существующих настроек. Новая миграция добавляет только Email сайта для заявок. Миграции запускаются на копии/новом стенде перед публикацией и после backup БД. Не применять `--fake` как способ скрыть ошибку.

## 3. Контактные формы

`/contact-us/`, `/partners/`, `/subscription/` используют обычный POST с CSRF, валидацией, согласием, honeypot и ограничением повторов сессии. JavaScript и таймер не подменяют отправку. При SMTP-ошибке или результате отправки 0 возвращается 503 и введённые данные остаются в форме. После успеха используется redirect, обновление страницы не посылает второе письмо.

Получатель: «Настройки сайта → Email сайта для заявок». Если пусто — `CONTACT_EMAIL`; если и он пустой — адрес из `DEFAULT_FROM_EMAIL`. Отправитель — настроенный серверный адрес, пользовательский email передаётся только как Reply-To. В production console/dummy/locmem/file backend не может показать успешную отправку. SMTP подтверждение означает приём письма транспортом, а не гарантированное попадание во входящие адресата.

Кнопки страницы подписки отправляют заявку менеджеру; сами по себе они не подключают автоплатежи. Реальные повторные заказы остаются в штатном checkout.

## 4. Заказ

Карточка содержит сохранённые названия/характеристики, количество и цены позиций, итоги, скидку, доставку, адрес, получателя, контакты, комментарий, трек и организацию. Характеристики берутся из снимка заказа, а не изменяемого каталога; удаление варианта товара не скрывает состав заказа. Для ПВЗ показываются полный сохранённый адрес и код. Чужой заказ возвращает 404.

## 5. ЮKassa и СДЭК

Дубли объявлений ЮKassa убраны. Все пути оплаты читают одни Django settings из окружения; test/live в ЮKassa определяется магазином и его парой ID/secret, а не отдельным флагом в шаблоне. [Официальная инструкция](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).

СДЭК использует одну действующую реализацию. Пустой `CDEK_API_URL` выбирает endpoint по `CDEK_TEST_MODE`; явный URL с противоречащим test/live флагом вызывает понятную ошибку до сетевого запроса. [Официальные адреса](https://apidoc.cdek.ru/): рабочий `https://api.cdek.ru/v2`, тестовый `https://api.edu.cdek.ru/v2`. Ключи тоже должны принадлежать соответствующей среде.

После изменения env пересоздать web и workers: изменение файла не меняет окружение уже работающего процесса. Проверка конфигурации без вывода секретов и без сетевых запросов:

```bash
python manage.py check_integrations --require-configured
```

Эта команда не подтверждает действительность ключей и не создаёт платёж или накладную. Реальная приёмка на сервере требует отдельно проверить SMTP, авторизацию СДЭК, создание/оплату заказа, webhook, сверку статуса и отсутствие повторной накладной. Настоящий платёж и отправку в СДЭК выполнять только с разрешения владельца. Ошибка подключения по SSH не является доказательством неработающей оплаты.

## 6. Контейнер

Docker устанавливает `requirements/prod.txt` с согласованным constraints. Несуществующий корневой requirements.txt не используется. Статика собирается без production-секретов и без `|| true`. Runtime entrypoint запускает миграции только при явном `RUN_MIGRATIONS=1`; в локальном compose этот флаг включён, в существующей production-схеме остаётся явный predeploy шаг.

```bash
docker compose -f compose.local.yml up --build -d
docker compose -f compose.local.yml ps
docker compose -f compose.local.yml logs web
```

В production не подставлять локальный секрет и не использовать `config.settings.local`. Не удалять named volumes с рабочими данными при обновлении.

## Регрессионная проверка и публикация

В отдельном окружении с dev requirements:

```bash
sh deploy/verify.sh
```

Команда использует только test settings и отдельную тестовую БД. До установки новой версии на рабочем сервере нужны backup, review и разрешённый SSH/VPN доступ. Эти изменения не считаются опубликованными только по факту commit или успешного теста.
