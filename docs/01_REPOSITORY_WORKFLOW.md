# 1. Репозитории, ветки и выпуск изменений

Актуально на 19.07.2026.

## Источник истины

Основной репозиторий проекта:

```text
https://gitverse.ru/sttrv_r/AspectCoffee.git
```

Единственным источником истины должен быть GitVerse. Каталог `/opt/aspectcoffee` на сервере — рабочая копия для развёртывания, а не отдельный основной репозиторий. Исправления на сервере сначала оформляются в ветку и отправляются в GitVerse; после этого сервер получает проверенный коммит.

Чистый снимок работающего сайта подготовлен в ветке:

```text
production-clean-20260719
```

Она основана на `main` GitVerse и не перезаписывает основную ветку напрямую.

## Назначение веток

| Ветка | Назначение | Разрешённый способ изменения |
|---|---|---|
| `main` | Принятая стабильная версия | Только запрос на слияние после тестов и ревью |
| `develop` | Общая интеграция незавершённых функций, если команда действительно использует этот процесс | Запросы на слияние из `feature/*` |
| `feature/<задача>` | Новая функция | Свободные коммиты автора, затем запрос в `develop` или `main` |
| `fix/<задача>` | Исправление | Запрос в `main` |
| `hotfix/<задача>` | Срочное исправление продакшна | Ускоренный запрос в `main`, но без обхода тестов |
| `release/<дата>` | Неизменяемый снимок выпуска | Создаётся из принятого `main`, затем помечается тегом |
| `archive/*` | Исторические снимки | Только чтение, слияние запрещено |

Существующие `container-live-code`, `fix/checklist-2026-07-08` и похожие ветки являются историческими/рабочими снимками. После принятия чистой ветки их следует пометить тегами и удалить либо переименовать в `archive/*`, чтобы разработчики случайно не продолжили работу от устаревшей базы.

## Защита `main` в GitVerse

В профиле репозитория откройте **Настройки → Защита веток** и создайте правило для `main`:

- запретить прямой push;
- запретить force-push и удаление;
- разрешить слияние только через запрос;
- требовать минимум одного согласования;
- требовать успешные проверки CI;
- отдельно защитить `.gitverse/workflows/**`, `docker/**`, `docker-compose.yml`, `config/settings/**` и миграции.

GitVerse позволяет отдельно ограничивать прямую отправку, слияние и изменение защищённых файлов: [официальная документация по защите веток](https://gitverse.ru/docs/collaborative/repositories/guides/pull-requests/branch-protection/).

## Дублирующие репозитории и зеркала

Дублирующий репозиторий допустим только как зеркало/резервная копия. Разработку в двух независимых «основных» репозиториях вести нельзя.

### Включить поступление изменений из дубля

1. Назначить GitVerse основным репозиторием.
2. В дублирующем репозитории создать отдельный технический токен с минимальными правами.
3. Направлять изменения в отдельную ветку `mirror/<источник>`, не в `main`.
4. Сливать `mirror/<источник>` в `main` только через запрос, тесты и ревью.
5. Если используется CI-зеркалирование, хранить токен только в защищённом секрете CI.

### Отключить поступление изменений из дубля

1. Отключить workflow зеркалирования/CI.
2. Отозвать технический токен или удалить deploy key.
3. Запретить push/merge для шаблона `mirror/**` правилом защиты.
4. Архивировать дублирующий репозиторий либо оставить его только для чтения.
5. Проверить, что на продакшн-сервере `origin` указывает на основной GitVerse.

При зеркалировании с `--force` целевой репозиторий полностью перезаписывается, поэтому такой режим нельзя направлять на рабочий `main`: [официальная документация GitVerse по зеркалам](https://gitverse.ru/docs/collaborative/repositories/guides/repository-workflow/mirroring-uc/).

## Рабочий цикл

```bash
git switch main
git pull --ff-only origin main
git switch -c fix/short-description

# изменения, тесты
git add <проверенные-файлы>
git commit -m "fix: краткое описание"
git push -u origin fix/short-description
```

После этого создаётся запрос на слияние в GitVerse. На сервер попадает только принятый коммит:

```bash
cd /opt/aspectcoffee
git fetch origin --prune
git switch main
git pull --ff-only origin main
docker compose build
docker compose run --rm web python manage.py migrate
docker compose run --rm web python manage.py collectstatic --noinput
docker compose up -d
```

## Выпуск и откат

Перед выпуском:

1. Сделать резервную копию `db.sqlite3` и `media/` вне каталога проекта.
2. Зафиксировать текущий коммит: `git rev-parse HEAD`.
3. Запустить тесты и `python manage.py check --deploy`.
4. Применить миграции и пересобрать контейнеры.
5. Проверить вход, корзину, оплату, СДЭК, OAuth и уведомления.
6. Создать тег `release-YYYYMMDD-HHMM`.

Откат выполняется на конкретный тег/коммит с восстановлением совместимой резервной копии базы. Нельзя откатывать только код, если уже применены необратимые миграции.

## Токены

Токен GitVerse не должен находиться в `.git/config`, shell history или документации. Для постоянной работы предпочтителен SSH deploy key. Если используется персональный токен, его следует ограничить репозиторием, хранить в менеджере секретов и немедленно отзывать после утечки: [официальная документация GitVerse по токенам](https://gitverse.ru/docs/collaborative/authentification/tokens/).
